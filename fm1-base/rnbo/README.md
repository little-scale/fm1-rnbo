# RNBO on FM1: first executable port

This is an isolated RNBO Minimal Export experiment beside the pinned `template` application. The existing template, platform sources and upstream build tools have not been changed. The RNBO experiment is now installed on the FM1.

The bundled monophonic RNBO instrument runs through the complete FM1 host simulator and now builds with the actual JieLi compiler and linker. The current 610,136-byte `FM-1_9300` package passes the post-build package/ELF review, including retention of the RNBO global startup initializer at `0x02008f32`. The earlier `.ctors` startup defect is fixed. The installer log confirms installation and restart as `FM-1_9300`; the user confirms it boots and works well on 28 October 2026. Basic hardware operation is confirmed; peak audio timing, xruns, stack usage and long-duration stability remain unmeasured. This agent's execution environment denies Docker access and cannot open a CoreMIDI client; the Finder launchers use the user's normal Terminal.

## Find this project on your Mac

This is inside your existing folder, not a separate workspace you need to download. In Finder, press **Command–Shift–G** and paste:

```text
fm1-base/rnbo
```

You can double-click `Verify-RNBO.command` to run all the host checks, or `Build-RNBO.command` to attempt a device build from your normal Terminal environment. The scripts locate the workspace and dependencies themselves. Neither script installs firmware. An `RNBO` shortcut in the top-level `FM1 Firmware` folder also leads here.

## What works on the host

- Actual C++ generated by the locally installed RNBO 1.4.4 code generator, with the generated licence preserved.
- 44.1 kHz, fixed 256-sample vectors, stereo output, float32 sample values and 64-bit RNBO scheduler timestamps.
- MIDI-controlled sine oscillator and ADSR, with exposed `level`, `attack` and `release` parameters.
- A freestanding C++11 adapter, linked using the C linker without libc++/libstdc++.
- An aligned 128 KiB monotonic allocation arena. This patch uses 65,632 bytes in two allocations on this Mac. Its inline patch state and working output arrays are additional memory; target object sizes will differ.
- Bounded UI command queue and one audio owner for the patch. The FM1 application merges keys and MIDI into one last-note-priority voice, including returning to a held lower note.
- K1/K2/K3 parameter controls, octave buttons, PLAY panic, and settings save/reload in the host simulator. Displayed parameter values are normalized percentages.
- MIDI, pitch, velocity, release, gain, invalid-input and reconstruction checks; a 116-second sustained render without late allocations or runtime errors; undefined-behaviour sanitizer checks.
- A host LLVM IR audit of the generated DSP loops. Software-double arithmetic remains permitted outside sample loops only in the experimental device build; it still needs target disassembly and timing review.
- An additional 32-bit freestanding ARM compile and single-precision-FPU IR audit. This is an ABI proxy, **not FM1 machine code**. The probe has 4-byte pointers/integers/samples and 8-byte timestamps; its compiled patch object is 14,856 bytes after the string-member compatibility fix, in addition to the arena and output buffers.
- A second 32-bit compile/IR check with WebAssembly's unsigned-long `size_t`, matching the specific JieLi typedef requirement that the ARM proxy does not reproduce. It caught the same allocation-operator error as the actual JieLi compiler before the typedef fix. This is a compile-only compatibility check, not a browser runtime.
- A dependency-closure check against the actual pinned JieLi maths and compiler-runtime archives. The required float maths and representative double primitives resolve without an additional libc. The actual pi32v2 link has now also succeeded.
- A C++11 compatibility adaptation for generated `DataRefStrings`. JieLi Clang 4 otherwise leaves undefined references to its `static constexpr auto&` string members. Immutable instance pointer members preserve the strings without separate definitions or heap allocation; their small storage cost is included in the compiled layout probe.

No browser patch uploader, patch-module loader, audio-input effect routing, Bluetooth, polyphonic instrument shell, is implemented. Basic on-hardware boot and sound are confirmed; broader hardware validation remains pending. The current UI exposes the first four parameters; the bridge accepts at most sixteen. The example has three.

## Reproduce everything

From the enclosing workspace:

```sh
source setup/env.sh
python3 fm1-base/rnbo/tools/verify.py
```

The exporter discovers your installed RNBO package. Set `RNBO_DIR` if needed. Its internal JavaScript API is deliberately pinned to 1.4.4; it fails on another version rather than silently using an incompatible generator. No installed RNBO package files are edited.

Verification writes logs and `summary.json` under `build/verification/`. Audio is at `build/rnbo-audition.wav`; simulator screenshots and a MIDI recording are under `build/panel/`. These are **host-generated**, not FM1 recordings. Native rendering speed is not a prediction of FM1 CPU load.

`tools/test.py --sanitize` uses UBSan. AddressSanitizer is available as `--asan`, but could not be validated in this environment: an empty ASan executable also timed out. Each subprocess has a timeout.

## Edit in Max

Open `patches/mono.maxpat`, generated from `patches/mono.rnbopat`. It embeds the RNBO patch and a MIDI input. The DAC starts off. The generated Max wrapper has not been opened in Max for UI verification; code generation and C++ execution are verified separately.

The reproducible source for this probe is `mono.rnbopat`. The exporter regenerates the wrapper; changes made only to the wrapper do not automatically flow back into that source. For a normal Max workflow, export the edited RNBO subpatch as `.rnbopat` and explicitly use it as the exporter input:

```sh
node fm1-base/rnbo/tools/export.cjs /absolute/path/to/your.rnbopat
```

This helper supports self-contained RNBO patches. It does not resolve external abstractions, external gen files or sample-file dependencies. The audio and panel regressions are specific to the bundled three-parameter instrument; an edited instrument needs its own expected results. `tools/audit.py` and `tools/build.py --host` can still be used as portability checks.

The bridge currently requires zero audio inputs and exactly two outputs. Do not assume an arbitrary exported patch will fit or meet the device deadline.

## Important portability fixes

1. **RNBO `mtof` is too costly for this starting budget.** Its default table requested 65,536 float entries: 256 KiB, before the oscillator table and patch state. The example uses `440 * exp((note - 69) * log(2)/12)` at event rate instead. The remaining oscillator table is 64 KiB.
2. **`RNBO_USE_FLOAT32` is insufficient by itself.** Unsuffixed generated literals promoted several envelope and oscillator expressions to double. `tools/float32.cjs` suffixes decimal floating-point literals, skipping comments, strings, integer literals and existing suffixes. Original generated code is kept as `rnbo_source.raw.h`. This is a deliberate float32 adaptation; it changes rounding. Separately, `tools/runtime.cjs` adapts `RNBO_Std.h` to use the compiler's `__SIZE_TYPE__` and `__INTPTR_TYPE__`: JieLi's 32-bit `size_t` is unsigned long, which RNBO's original unsigned-int fallback gets wrong. The original header and both hashes are preserved in `export/originals/` and `provenance.json`. The installed RNBO package is untouched.
3. **Scheduler timestamps remain double.** Their type and RNBO's 64-bit assertion are retained. The IR audit checks arithmetic in cyclic blocks of generated `*_perform` functions and their direct/transitive callees, not all possible patch behaviour or target code generation.
4. **The firmware has C startup.** The device build derives a linker script which retains both `.init_array` and legacy `.ctors` tables in XIP. JieLi Clang 4 uses `.ctors`; keeping only `.init_array` silently discarded the global initializer despite a successful link. The adapter executes legacy constructors in reverse order, skips their optional sentinel pointers, then executes `.init_array` forward, once before patch construction and audio startup. It then explicitly constructs the patch and its allocation-free logger. The post-build review requires the RNBO initializer to appear in the retained tables. This matters for RNBO's `EXP2_NEG23`: under freestanding `-fno-builtin` compilation, its `exp2f(-23)` initializer is a runtime call rather than a folded constant. The helper PRNG is also initialized. The IR audit reviews those constructor calls; further global constructors require review.
5. **Allocation is bounded, not a general-purpose heap.** `free` is a no-op until whole-patch reconstruction. Growth/reallocation consumes more arena space. Any allocation after startup is counted and causes rendering to mute; pool exhaustion takes the target to watchdog reset. This is suitable for the bundled preallocated probe, not arbitrary buffer resizing or unbounded lists.
6. **USB playback is mixed after the application by the current platform.** It is not routed into RNBO as an effect input.

The generated header, raw header, runtime-header hashes, source-patch hash and prepared-patch identity are recorded in `export/provenance.json`. Saved settings are invalidated when the prepared patch changes.

## Device build and hardware trial

From a terminal with access to the existing Docker Desktop engine:

```sh
source setup/env.sh
python3 fm1-base/rnbo/tools/build.py --device --experimental-soft-double
```

This command **builds only; it never installs firmware**. It uses the existing pinned JieLi compiler, SDK packaging files and Docker image. It adds a C++ compilation unit and links the toolchain's r3 maths/compiler support archives. It derives its build and linker behaviour locally without editing the upstream builder.

The explicit `--experimental-soft-double` switch permits RNBO's expected double support in this experiment while retaining the other upstream checks. Without it, the upstream no-double policy remains in force. This switch does not prove the remaining double operations are cheap or confined to safe locations on the target.

The actual compile, link and post-build review succeeded, with image 96,160 / 581,564 bytes, static RAM 32,712 / 98,304 bytes and pool 176,144 / 344,064 bytes. Runtime stack high-water and on-device audio timing remain unmeasured. The package SHA-256 is `6151904bcc991269cb098138a375009b70265a7bfb8981d57b3560c448d73f49`. The earlier linked package was rejected by the startup review; the current package includes the retained legacy constructor and passes.

`tools/review-device.py` checks package identity, UFW header/list/payload CRCs, exact app/SDK and loader payloads, ELF entry/load images, undefined globals and retained constructor pointers. It records hashes, memory and identifiable software-double calls in `build/device-review.json`. The pinned disassembler cannot decode some FPU instructions, so a complete target DSP-loop audit remains unverified.

After a successful rebuild and review, double-click `Install-RNBO.command`. This checks the package again, then uses the upstream installer's normal `Install? [y/N]` prompt. It replaces the current firmware only after `y`; no Docker is required. Output is saved in `build/install.log`. Connect the FM1 by USB and lower its audio volume before the first notes. Expect `RNBO / MONO PROBE`, sine notes, K1 level, K2 attack, K3 release, octave buttons, PLAY panic and SAVE settings. Try held/overlapping notes and USB MIDI, and check CPU and the fault line. Then test a power cycle and saved settings. Audible operation and displayed CPU alone do not prove worst-case callback timing or absence of xruns.

On hardware, measure peak callback time and xruns against the roughly 5.8 ms deadline, and check stack guards. The local development identity is `FM-1_9300`; it is not a community-reserved identity.
Only after a successful build and target review should an installation be considered. The known-working template and the stock V15 restore package remain available in the enclosing workspace.
